# Gateway Troubleshooting Reference

Session-specific breadcrumbs and diagnostic patterns for gateway errors.

## Error Source Classification

When a gateway user reports an error, classify it by log file before investigating.

| Error symptom | Check this log | Source |
|---|---|---|
| "Cannot connect to host", "poll error", "connect failed" | `gateway.log` | Platform adapter (network/DNS/proxy) |
| "Non-retryable client error: Error code: 4xx" | `errors.log` or `agent.log` | LLM model API call (run_agent.py) |
| "Transient agent failure" | `errors.log` + `gateway.log` | Agent had an API error but recovered via fallback |

The HTTP 4xx/5xx error messages (`⚠️ Non-retryable error (HTTP 400) — trying fallback...`) are generated by `run_agent.py` (line ~12600), NOT by the WeChat/Telegram adapter. They indicate the model provider (OpenRouter, DeepSeek, Ollama, etc.) rejected the request.

## Gateway Config Independence

The gateway is a **separate long-lived process** (launchd on macOS, systemd on Linux). It reads `config.yaml` at startup and does NOT pick up CLI session model switches (`hermes model`, `-m` flags). 

To verify what model the gateway is using:
```bash
# Check the gateway process's config.yaml (NOT the current CLI session)
hermes config | grep "Model:"
```

Diagnostic: if a message reaches the gateway but processing fails with an LLM API error, and the user just switched models in their CLI session, the gateway is still using the old config.yaml model. Fix: `hermes config set model.*` then `hermes gateway restart`.

## Config.yaml Platform Structure

The gateway reads platform config from the **top-level** `platforms:` key in `config.yaml`. NOT under `gateway:`.

```yaml
platforms:
  weixin:
    enabled: true
    token: e81004a40e7e@im.bot:06000085c34f20ad9c8deb0dd2ca04bfc32837
    extra:
      account_id: e81004a40e7e@im.bot
      base_url: https://ilinkai.weixin.qq.com
  telegram:
    enabled: true
    token: "123456:ABCDEF..."
```

The token can also be supplied via env vars (`WEIXIN_TOKEN`, `TELEGRAM_TOKEN`), with config.yaml taking priority.

## Gateway Restart Behavior

When `hermes gateway restart` runs:
1. Sends SIGTERM to the running gateway process (launchd/sytemd managed)
2. The old gateway drains active sessions and exits
3. A **new** gateway process starts from scratch
4. The new process reads fresh `config.yaml` — **no platform configs survive unless explicitly in config.yaml or .env**
5. Previously-configured platforms that used env vars in the original shell (not in `.env`) will be lost

Common pitfall: after `hermes gateway restart`, users expect all previously-working platforms to come back automatically. They will NOT unless the platform config is persisted in `config.yaml` or `.env`.

Before restarting, verify which platforms are persisted:
```bash
grep -A2 "platforms:" ~/.hermes/config.yaml  # check config.yaml
grep -i "WEIXIN\|TELEGRAM\|FEISHU" ~/.hermes/.env  # check .env
```

## Gateway Platform Configuration Methods

Platform credentials can be configured in three ways, listed in priority order:

1. **`config.yaml` top-level `platforms:` key** (highest priority) — persists across all restarts
2. **Environment variables in `.env`** — persists across restarts managed by launchd/sytemd
3. **Shell environment variables** (lowest priority) — lost on restart unless set in `.zshrc`/`.bashrc`

Best practice: put platform credentials in `config.yaml` under `platforms:` for persistence.

## User Pairing / Approval

When a user sends a message to a gateway bot for the first time, the gateway generates a pairing code. The bot responds with instructions like "Reply with your pairing code: XXXXXX". To approve:

```bash
hermes pairing approve <platform> <code>
# Examples:
hermes pairing approve telegram 6WCF3KP5
hermes pairing approve weixin ABC123
```

The pairing code is shown in the user's DM with the bot on the respective platform. After approval:
- The user ID is saved to `~/.hermes/pairing/{platform}-approved.json`
- The user is recognized on their next message
- No `hermes gateway restart` needed — takes effect immediately

Alternatively, pre-approve users by adding `allow_from` in the platform's `extra` config:

```yaml
telegram:
  enabled: true
  token: "..."
  extra:
    allow_from: "7799184011"  # comma-separated user IDs
```

## WeChat/Weixin Diagnostics

### iLink Bot Protocol

Hermes connects to WeChat personal accounts via Tencent's iLink Bot API at `ilinkai.weixin.qq.com`. This is NOT an unofficial hack — it's Tencent's official bot protocol for personal WeChat accounts. The adapter is at `gateway/platforms/weixin.py` (~2100 lines).

### DNS / Proxy Interference

DNS resolution of `ilinkai.weixin.qq.com → 198.18.x.x` (RFC 2544 benchmark range) is a telltale sign that a local proxy (Clash, Surge, V2Ray, ClashX) is intercepting the connection. This range is reserved for Benchmarking and commonly used as "fake IP" by proxy software.

The gateway auto-detects proxies:
```
Proxy detected; passing explicitly to HTTPXRequest: http://127.0.0.1:7890
```

If the proxy is running but DNS still fails, check that the proxy routes `*.weixin.qq.com` traffic correctly.

### WeChat Account Files

Stored at `~/.hermes/weixin/accounts/`:
- `{account_id}.json` — token, base_url, user_id
- `{account_id}.context-tokens.json` — per-peer context tokens (iLink session state)
- `{account_id}.sync.json` — sync buffer for polling

Pairing files at `~/.hermes/pairing/`:
- `weixin-pending.json` — users waiting for approval
- `weixin-approved.json` — approved users (auto-managed)

### Common Errors

- **"Non-retryable error (HTTP 400)" during WeChat message processing** — NOT a WeChat error. The LLM model API (Ollama/DeepSeek/etc.) returned 400. Check `errors.log` for details.
- **"Cannot connect to host ilinkai.weixin.qq.com:443"** — DNS failure or proxy not running. Check `gateway.log` for proxy detection messages.
- **"Unauthorized user: ...@im.wechat"** — user needs approval. The gateway auto-manages this via the pairing system; check `weixin-pending.json`.
- **"Unauthorized user: ...@im.bot"** — the iLink bot's own identity ID. Ignore or approve — it's self-referential and harmless.
- **iLink `errcode: -14` (session expired)** — the iLink session token expired. The adapter auto-retries without `context_token` as a degraded fallback.

### WeChat Token Format

The token in `{account_id}.json` follows a specific format: `{account_id}:{hex_token}`. The `account_id` appears as a prefix in the token value itself. When configuring in `config.yaml`:

```yaml
weixin:
  enabled: true
  token: "e81004a40e7e@im.bot:06000085c34f20ad9c8deb0dd2ca04bfc32837"  # <-- account_id:hex_token
  extra:
    account_id: e81004a40e7e@im.bot
    base_url: https://ilinkai.weixin.qq.com
```

The three pieces come from the accounts JSON — always copy all three when setting up WeChat.

### Channel Status on WeChat

The WeChat bot shows a status indicator at the top of the conversation (the "clawbot" label area). Messages like "暂时无法连接 OpenClaw" indicate the WeChat bridge service itself has connectivity issues — check DNS, proxy, and whether `ilinkai.weixin.qq.com` is reachable.

## Telegram Diagnostics

### Connection

Telegram connects via long polling (default) or webhook mode. The gateway auto-detects local proxies and passes them to HTTPXRequest:

```
[Telegram] Proxy detected; passing explicitly to HTTPXRequest: http://127.0.0.1:7890
```

### Fallback IPs

When the primary Telegram API (`api.telegram.org`) is unreachable (often DNS-related), the gateway auto-discovers fallback IPs:

```
[Telegram] Auto-discovered Telegram fallback IPs: 149.154.166.110
```

If DNS for `api.telegram.org` returns fake IPs (same `198.18.x.x` range as the WeChat issue), the proxy handling the DNS should route `*.telegram.org` correctly.

### Common Errors

- **"Connect attempt N/8 failed"** — DNS or proxy issue. Same `198.18.x.x` fake-IP problem as WeChat. Ensure proxy is routing `api.telegram.org`.
- **Telegram bot silent** — Bot token may be invalid. Check with `curl https://api.telegram.org/bot<TOKEN>/getMe`.
- **"Telegram menu: 100 commands registered, 26 hidden"** — Normal. Telegram limits the bot command menu to 100 entries.

## Feishu / Lark Diagnostics

### Connection Mode

Feishu connects via WebSocket (`wss://msg-frontier.feishu.cn/ws/v2`). It auto-reconnects on disconnect:

```
[Feishu] trying to reconnect for the Nth time
[Feishu] connected to wss://msg-frontier.feishu.cn/ws/v2?...
```

Common disconnect reasons ("no close frame received or sent", "ping_timeout") are typically network blips — Feishu auto-reconnects on its own.

### Common Errors

- **"connect failed, err: NameResolutionError"** — Same proxy/DNS issue as WeChat/Telegram. Ensure `open.feishu.cn` is routed through your proxy.
- **"receive message loop exit"** — Normal WebSocket disconnect; Feishu reconnects automatically.

## Cron Job Delivery Failures (Mac Sleep)

Cron jobs that deliver to messaging platforms (Telegram, WeChat, etc.) require the gateway to be running AND the network stack to be available at execution time.

### Symptom

```
delivery error: Telegram send failed: httpx.ConnectError: [Errno 8] nodename nor servname provided, or not known
```

The job runs (generates the content), but the delivery step fails with a DNS resolution error.

### Root Cause

Mac was asleep at the cron trigger time. When macOS sleeps:
- Wi-Fi disconnects (or goes to low-power mode)
- DNS resolver is unavailable
- The gateway is still running (launchd keeps it alive), but network calls fail

The cron scheduler fires the job, the agent generates the response, but the messaging delivery hits DNS failure because the network isn't ready.

### Diagnosis

```bash
# Check last run status
hermes cron list --all
# Look for: last_status: "error", last_delivery_error contains "ConnectError" or "nodename nor servname"

# Check if the run time was during typical sleep hours
# e.g. 0 8 * * * → 8 AM — if Mac was asleep at 8 AM, this is the culprit
```

### Fixes

**Option A: Delay the cron time** (simplest)
```bash
hermes cron edit <job_id>  # change schedule to e.g. 0 8:30 * * * (gives Mac 30 min to wake)
```

**Option B: Prevent Mac sleep before cron**
- Use **Amphetamine** (App Store) to schedule a wake period starting 5 minutes before the cron time
- Set a scheduled wake in **System Settings → Battery → Schedule**

**Option C: Manual re-run** (one-time recovery)
```bash
hermes cron run <job_id>  # triggers the job to run on next tick
```

The content generation already completed — only the delivery failed. A manual `cron run` sends the generated content.

### Prevention

- If Mac regularly sleeps overnight, schedule cron jobs at times when Mac is likely awake (e.g. 9 AM instead of 8 AM)
- For critical early-morning jobs, use **Amphetamine** or macOS **pmset** to schedule a wake:
  ```bash
  sudo pmset schedule wake "2026-05-21 07:55:00"
  ```

## Log Location Reference

| Log file | Purpose |
|---|---|
| `~/.hermes/logs/gateway.log` | Gateway lifecycle, platform connections, message events, platform adapter errors |
| `~/.hermes/logs/errors.log` | LLM API errors (Non-retryable client error, auth failures, model errors) |
| `~/.hermes/logs/agent.log` | Agent session detail (context compression, tool calls, per-session errors) |
